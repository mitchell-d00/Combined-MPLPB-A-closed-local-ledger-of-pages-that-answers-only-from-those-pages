# Gremlin: remember components, boundaries and useful unfinished work

Last reviewed: 2026-11-27.

Gremlin is a project-maintenance map for **product, project, data and experiments**.
It joins the existing department ownership and result/test indexes with explicit
component links, reuse candidates, and revisit conditions. It helps Betty find
what might be affected by a change and what prior work might help. It is a
lab/developer tool; it is not part of the reader's admission proof or the Git
effect controller.

## Use it before planning a change

```sh
python -m test_tools.gremlin check
python -m test_tools.gremlin show workflow-controller restart-store
python -m test_tools.gremlin impact mplpb_combined/ledger.py
python -m test_tools.gremlin impact evaluation/comparative-tests/workflow-controller/controller.mjs
```

`check` recomputes the map from tracked files and rejects stale generated bytes.
It detects changed content, path additions/removals, broken references, duplicate
IDs, unknown relationship endpoints, and missing department ownership. `show`
returns structured component records from the saved snapshot. `impact` gives direct matches, declared
dependents, relevant evidence links and open work. It is a review aid with an
incomplete curated graph; it is not an exhaustive dependency analysis. Both
queries explicitly report snapshot-only freshness. Run `check` first to validate
the snapshot against current tracked bytes; queries do not rehash the full
repository every time.

## Keep it active

After an implementation, dependency, fixture, result or packaging change:

1. Inspect the map and use `impact` on the changed paths. Review the existing
   department map and result index; they remain authoritative for those fields.
2. Update `registry.json` when a component, relationship, boundary or revisit
   condition has changed. Explicitly record the actual review date. A relation's
   `basis` is source, documentation or proposal. Merely finding a file does not
   establish the relation's truth.
3. Stage intended files, then run `python -m test_tools.gremlin refresh` and `check`.
4. Regenerate the repository handoff after the map and other source changes.

The dedicated Gremlin workflow checks freshness and its tests. It does not
auto-commit a map or alter existing release acceptance rules. A newly added
tracked root must first receive department ownership. Untracked local files and
private custody are outside the inventory. In an extracted source ZIP, Gremlin
uses the handoff's tracked path list. New files in such an extraction must be
registered by returning to a Git checkout and updating the handoff.

The generated output includes content fingerprints across tracked files and
SHA-256 references to specific evidence files. It hashes archives as opaque
bytes; it does not unpack them, extract passages, read held off-repository
inputs, or import the modules it maps. File contents are not copied into the
map. A hash match establishes byte identity, not permission, support or truth.

Generated map files and the self-containing handoff/update files are explicitly
excluded from component content digests to avoid recursive hashes. Their path
names are still counted. The repository handoff independently inventories the
finished generated map. Stage before refresh so new tracked paths are visible.

## Links preserve separation

The four responsibility labels may overlap. Department ownership does not mean
every file in that department ships. Packaging boundaries remain in
[the distribution manifest](../PRODUCT_DISTRIBUTION.json) and
[the responsibility map](../RESPONSIBILITY_BOUNDARIES.md). Study scopes, grades,
custody and NOT_RUN labels remain in [the result index](../results.json) and
their pinned reports. Some index strings describe historical checkpoints;
Gremlin copies them with that warning and never treats them as current release
certification.

The graph is directional. `depends_on` and `uses_data` propagate conservative
change-review hints. `tested_by` supplies a check/evidence pointer, not a pass.
`records` links an inventory or coordination surface. `possible_reuse` is a
proposal and does not propagate as an established runtime dependency.

## Effect-stack goal

The roadmap is ledger → reader → policy → executor → readback → recovery.
Gremlin records where each responsibility lives, the evidence for its current
boundary, and what would need review before extending it. It must preserve the
separate states **admitted, attempted, observed and durably recorded**.

Git is the first tested laboratory adapter. File and deployment adapters remain
proposed; Git's old-value check does not establish their behavior. A map edge
never grants an action, authenticates a role, makes an experiment independent,
changes a release gate, or promotes a candidate into the product.
